## Implemented action path

`CoupledPolicy` runs the original OFT policy once to obtain prompt features,
eight action-slot states and an initial eight-action proposal. It decodes the
proposal into executable simulator actions, re-normalizes and detaches it,
then pads it to 32 steps. Every action anchor receives a horizon-8 prediction,
independent of demonstrated future availability.

The action head receives all 128 × 256 future-core tokens through the specified
FP32 cross-attention block: 2,048-dimensional queries, eight heads of width 32,
affine LayerNorm, biased Q/K/V projections and a zero-initialized output map.
It adds exactly **1,187,072 parameters** to either arm. The same OFT head then
produces the final eight actions. Per deployed inference query, there is one
backbone call, one future-core call and two calls to the same action head.
Training batches run candidate futures in chunks of at most 10 anchors, preserving
their order and gradients; the 10+1 boundary is explicitly tested. All candidate
graphs remain live until the joint backward, so memory admission still needs
the actual full-batch pilot.

The proposal's affine conversion uses FP64 to match the existing NumPy simulator
decoder, then returns FP32 conditioning. Future-network and attention arithmetic
remain FP32. Clipping normalized predictions directly would produce different
physical actions under the frozen nonidentity statistics.

The implementation is split into:

- [`coupled_policy.py`](../src/eventground_wam/coupled_policy.py): executable
  proposal, attention, action path, separate auxiliary backward, and disjoint
  four-group optimizer parameter inventory.
- [`future_core.py`](../src/eventground_wam/future_core.py): decoder-free view
  sharing the full predictor's core tensors. It executes the original pixel
  core forward verbatim with an identity decode hook; neither the pixel decoder
  nor JEPA target projection is registered or executed in the policy.
- [`coupled_setup.py`](../src/eventground_wam/coupled_setup.py): verifies the
  sealed design and parents, original CPT checksum, action statistics and fresh
  B0-matched shared tensors before construction. CPU and CUDA RNG streams are
  preserved while loading the future module; coupling initialization uses its
  own forked CPU seed.
- [`coupled_checkpoint.py`](../src/eventground_wam/coupled_checkpoint.py):
  checksummed inference exports containing allowlisted shared policy weights,
  the future core, attention and pinned normalizer metadata. Training-only
  output heads and frozen base weights are excluded. This is not a training
  recovery checkpoint or permission to initialize production from diagnostic weights.

## Training integration boundary

The full predictor and policy's core view share tensor identities. Use
`coupled_parameter_groups` to include those tensors exactly once, alongside
the shared head/state, LoRA and coupling groups. The four groups use learning
rate 1e-4; the training engine must apply the frozen AdamW settings, one joint
gradient clip, one optimizer step and one scheduler step per logical batch.

`forward_with_features` returns the final action output and live backbone
features through one shared live FP32 view of the BF16 backbone output.
This combines candidate and auxiliary adjoints in FP32 before returning them
to the backbone. `coupled_joint_backward` adds the existing teacher-forced Week 7
auxiliary loss through the original whole-batch implementation. It preserves
the pixel weight 4.836645309900765 and JEPA weight 1.5140534185764003, including
the cross-anchor variance rule. Demonstrated intervening actions are used only
by this separate auxiliary call. Candidate-conditioned futures are never
supervised against a future generated by a different demonstrated action sequence.

```python
model, predictor, lora_names, provenance = build_fresh_coupled_policy(
    source_root, cache_dir, device, arm="M3",  # or M4
)
groups = coupled_parameter_groups(model, predictor, lora_names)
# CoupledTrainingEngine now owns optimizer, scheduler and complete recovery.
# Zero all groups before each call; jointly clip and step once afterward.
result = model.forward_with_features(
    batch["inputs"], batch["proprioception"], batch["future_inputs"].current_images,
    normalized_action_targets=batch["targets"],
)
metrics = coupled_joint_backward(
    model, result, predictor, batch["future_inputs"], future_targets,
    microbatch=10,
)
```

The action API has no future-target, teacher-feature, demonstrated-action or
availability-mask argument. Proposal actions are detached; current backbone
features remain differentiable. Ground-truth loss targets are detached. At
zero initialization, action gradients reach the coupling output projection;
upstream attention and core gradients are expected to be zero through that
projection. Tests explicitly activate it before checking those gradient paths.

## Verification and limits

The [local tests](../tests/test_coupled_policy.py) cover:

- Exact attention parameter count, seeded initialization and unchanged RNG.
- Nonidentity action normalization, clipping in simulator units, zero-threshold
  gripper decoding, detachment and zero padding.
- Original predictor token equality, skipped training outputs, one-backbone /
  two-shared-head call counts and exact initial action/loss equality.
- Target isolation, future-token sensitivity, intended gradients and absence
  of gradients to the frozen base, proposal and target tensors.
- Direct joint loss versus inherited accumulated backward for both arms with
  microbatches 1/2/3; full logical-batch JEPA variance; missing horizon-8 targets;
  single-action short batches and empty auxiliary supervision.
- FP32 attention inside an outer autocast context, rejection of malformed input,
  strict export/reload equality, normalizer mismatch and damaged export detection.

## October 6 production integration follow-up

The new `coupled_training.py` engine and `train_coupled_policy.py` wrapper
implement four disjoint optimizer groups, one joint clip/update/scheduler step,
complete predictor/coupling/Adam/scheduler/RNG/exposure recovery, fixed endpoint
exports, and persistent resource accounting. Production is gated by the separate
`check_coupled_training.py` actual-host qualification. No accepted Week 7 source
was edited. The user provisioned Lambda A100 SXM4 40 GB `129.146.69.183` for M4
first; its software matches the original pinned Python/PyTorch/CUDA packages.

The current local verification has 74 passing tests: 43 coupling/engine/production
cases and 31 inherited auxiliary/OFT cases. Both real-Qwen A100 interface smoke
checks passed. Full original-batch qualification is still required; see
[Week 8 status](WEEK8_STATUS.md) for the current launch decision.

The retained attempts first exposed a mismatched cuDNN reference context, then
joint BF16 gradient sensitivity. In pinned Torch 2.13,
`cudnn.flags(allow_tf32=False)` also defaults `enabled=False`; both the reference
and predictor must use the same context. A single live FP32 boundary removes
separate BF16 casts but does not guarantee the frozen 1% joint-gradient bound:
M3 still differed by 2.50% in attempt 06. Identical full-objective repeats agreed
exactly. Tiny FP32 microbatch differences (8.69e-7 relative L2 at the shared feature
boundary for M3) can cross BF16 rounding thresholds and amplify in Qwen backward.

The new explicit execution revision, `coupled-whole-logical-future-batch-v1`,
differentiates the full logical auxiliary objective directly, alongside the final
action loss. It stops at the shared FP32 feature boundary before propagating once
into the base under the base's original precision context. Candidate conditioning
retains microbatch 10. The engine recovery format and execution contract identify
this revision; old exploratory snapshots cannot resume into it. This requires
separate real-model correctness, recovery, memory and time admission in attempt 07.
The earlier microbatch implementation remains available as an unadmitted diagnostic.

The frozen architecture, losses, data order, optimizer, numerical tolerances and
resource caps are unchanged. No accepted Week 7 source was edited. Failed attempts
and diagnostic scripts/logs remain available, and no pilot weights may enter
production. The production service remains inactive until all applicable gates pass.
